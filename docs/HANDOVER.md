## 一、项目目标

Windows 手动长截图工具：用户手势为 `Ctrl+Alt+A` 进入模式 → 按住左键拖出选区 → 滚动滚轮（上/下均可，不混用）延长内容 → 松开左键，自动拼接保存为 PNG 并复制到剪贴板（CF_HDROP 文件，可直接 Ctrl+V 粘贴）。

## 二、文件清单（均在 D:\编程\PasteImage\）

| 文件 | 说明 |
|---|---|
| LongShot.ahk | 主交互脚本（AutoHotkey v2）：快捷键、拖选、绿/红选框、滚轮截帧调度、异步调起拼接 |
| stitch.ps1 | 拼接算法（PowerShell 5.1 + 内嵌 C# RowStitcher 类），本次交接的核心 |
| PasteImage.ahk | 用户原有工具（Explorer Ctrl+V 存剪贴板图片），**不要动** |

## 三、工作原理

1. **截帧**（LongShot.ahk）：首个滚轮事件锁定选区并拍第 0 帧；之后连续滚动按 `SettleMs=420ms` 节奏持续截帧（非重置调度），GDI BitBlt + GDI+ 存 PNG 到 `D:\Temp\LongShot_<tick>\f0000.png...`。
2. **拼接**（stitch.ps1）三阶段：
   - 去重：SHA256 剔除完全相同的连续帧（滚动没生效的帧）。
   - 链式对齐：逐对相邻帧求带符号位移 s（支持向上滚）。
     - 粗定位 `FindShift`：行 FNV 哈希（&0xF8 掩码）全扫描，动量排序，0.999 精确匹配优先 + 纯色守卫（重叠区 ≥6 个不同哈希），0.85 模糊回退。
     - 精对齐 `RefineShift`：在粗定位 ±16px 窗口内，**逐行置信度**重打分（当前版本带纹理加权，见下）。
   - 合成：按偏移画到大画布；对不上的帧整段追加（跳变 discont），内容永不丢失。
3. **交付**：保存到 `C:\Users\华为\Pictures\LongShots\LongShot_yyyyMMdd_HHmmss.png`，复制到剪贴板，删除帧目录（当前 `KeepFrames := true` 调试模式下保留）。

## 七、环境坑清单（前人踩过，勿重复）

1. AHK 拉起的 powershell 5.1 子进程**没有 Get-FileHash**（模块自动加载异常）——已改纯 .NET；新加 cmdlet 前先想替代方案。
2. AHK `Format()` 占位符**从 {1} 开始**，不是 {0}。
3. PNG 编码器 CLSID：`06 F4 7C 55 04 1A D3 11 9A 73 00 00 F8 1E F3 2E`（曾把 9A 73 写反导致全部 0 字节）。
4. DllCall 类型用 "uchar" 不是 "byte"。
5. 选框窗口必须 `+E0x20 +E0x80000` 组合，否则挡滚轮（页面滚不动）。
6. 上方副屏 y 为负坐标（如 -2131），坐标计算不可假设非负。
7. 用户环境 `A_Temp` = `D:\Temp`；`log`、`out` 是 AHK 内置名不能做变量。
8. AHK /validate 只查语法，DllCall/运行期错误只在运行时暴露。

## 九、2026-11-10 晚：v4 修复（视觉已裁决，机制已改，等用户手势复验）

### 9.1 先给结论：v2 / v3 都不对，正确高度是第三个数

用独立方法（逐对全范围纹理匹配，与 stitch.ps1 的实现无关）求 6 帧组的**真值**：

| 相邻帧 | 真实位移 |
|---|---|
| f0→f1 | 500 |
| f1→f2 | 400 |
| f2→f3 | 472 |
| f3→f4 | 743 |
| f4→f5 | 1013 |

即真实内容高度 = 1227 + 500+400+472+743+1013 = **4355**（裁掉 2px 描边后 4351）。
而 v2 = 3569（丢内容）、v3 = 5053（内容顺序错乱）。**v3 并不是"偏保守"，而是最后 2 帧放错了位置。**

- v2：f5/f1/f0 位置其实是对的，但 f2/f3/f4 在输出里**完全找不到**（内容被错误重叠吃掉）→ 内容塌缩仍在。
- v3：f3/f2/f1/f0 四帧**完全正确**（与真值一致），但 f4/f5 因为 JUMP 被堆到画布**底部**。
  用户是**向上滚**的，后截的帧属于更上方，所以 f4/f5 的正确位置是 f3 上方 743 / 1756 px。
  结果：输出读完正确内容后，又接了两段"更早的"内容 → 顺序错乱（不是重复，像素确实不同）。

### 9.2 三个真 bug（都已在 stitch.ps1 修掉）

1. **锚点 + ±16 窗口 → 绝大多数帧对直接放弃对齐**
   `FindShift`（行哈希、0.999 精确匹配）在文字页面上几乎必然失配（滚动非整数像素 → 抗锯齿），
   返回垃圾锚点后 `RefineShift` 只在 ±16px 内搜索 → 找不到真实位移 → JUMP。
   实测：12 帧组 11 次 JUMP（7548 = 629×12，等于 12 张图直接拼接）、19 帧组 15/18 次 JUMP、6 帧组 2 次。
   这解释了为什么 v3 在三个组上都"偏保守"——**它其实基本没对上过**。
2. **JUMP 只会往画布底部堆** → 向上滚动时整段内容被放到错误的一端（v3 的 6 帧组就是这样）。
3. **每帧都带 2px 选框描边** (0,176,80)，没裁 → 输出四周有绿框、接缝处有横贯全宽的绿线，
   而且这些行在任意位移下都"完全匹配"，污染对齐评分。

### 9.3 改法

- 新增 `RowStitcher.BestShift`：**全范围**纹理评分搜索（每个位移都试，粗扫每 6 行/24 字节采样 → 最优附近 ±6 逐行精扫），
  不再依赖哈希锚点。19 帧耗时约 3 秒。
  注意：这个评分函数**非常尖**（文字页 ±1px 就从 +96 掉到 −16），所以粗扫步长必须 ≤4，最终改为逐像素扫描。
- JUMP 改为**两遍法**：第一遍只求所有相邻位移并统计方向（up/down 计数），第二遍按多数方向决定追加到上方还是下方。
  注意 `$dir` 会和 `param([string]$Dir)` 撞名（PowerShell 大小写不敏感），已改名 `$scrollDir`。
- 新增 `RowStitcher.DetectBorder`：四角同色才认为是描边，按边裁掉 1~4px（本次实际 2px）。
  输出会窄 4px / 高 4px，属预期。
- 诊断增强：align 日志带 `[coarse/fine/matched/textured]`，新增 `dir= up= down=` 行；
  设环境变量 `LONGSHOT_KEEP_LOG=1` 可让 stitch.ps1 成功后也保留 `stitch_error.log`（AHK 调用不带该变量，仍是原行为）。
- 备份：`stitch.ps1.v3.bak`。

## 十、2026-11-10 晚（续）：两次真实手势样本 = 画面根本没滚动

### 10.1 结论先说

用户反馈"拼出来相当于没滑动，只有最后一帧，但提示成功"。拆帧后证实：**不是拼接算法错了，是截到的帧里画面一次都没动。**

- `D:\Temp\LongShot_63949953`（18 帧，1148×528，输出 528 高）
- `D:\Temp\LongShot_63923250`（14 帧，1230×857，输出 857 高）

把每帧贴成网格看（`D:\Temp\deveco\crops\m63949953.png`、`m63923250.png`）：18/14 帧都是**同一张聊天列表**，
只有预览文字/红点这类局部像素在变。程序侧独立验证：日志里每一对 `refined=0`，`matched` 高达 857/857、528/528，
即相邻帧按 0 位移完全重合 → offsets 全 0 → 输出高度 = 单帧高度。

滚轮其实发出去了（HUD `ticks` 一直在涨、帧数也在涨），但画面没滚。最可能的原因是
**松手时鼠标停在选框的右下角，那里是微信的聊天内容区（空白的），不是左侧可滚动的会话列表**，
滚轮落到了不滚动的面板上。注意选区在锁定后就不再变化，此时移动鼠标不会改选区，可以随便换位置再滚。

### 10.2 因此补的两处（都是"别再骗用户"）

1. `stitch.ps1`：新增"没滚动"判定——所有相邻帧位移都为 0 时，仍照常输出单帧图，但
   日志写 `noScroll=True`、stdout 变成 `OK <h> discontinuities=0 noscroll=1`，
   并在帧目录写一份 `stitch_status.txt`（日志默认成功即删，AHK 读不到）。
2. `LongShot.ahk`：
   - 每张新帧与上一帧比 PNG 字节（同一编码器同像素必得同字节），连续相同就当场弹提示
     "画面没有变化（N 次）…"，不用等拼接完。
   - `CheckStitch` 读 `stitch_status.txt`，`noscroll=1` 时提示"没有检测到滚动，输出只是单帧"，
     不再显示"已保存"了事。
   - `LongShot_band.log` 增加诊断：`locked rect=… active=<hwnd>(class) under=<hwnd>(class | title)`、
     每条 `wheel tick=… active=… cursor=(x,y) under=…`。下次复现可直接判断是"窗口没拿到焦点"
     还是"指针在不可滚区域"（`under` 若是 BandGui 的窗口，则是选框抢了滚轮）。

### 10.3 复验方法

1. 重新加载 `LongShot.ahk`（Ctrl+Alt+A 进入模式）。
2. 拖出选区后**把鼠标移到会滚动的正文/列表上**（选区已锁定，移动鼠标不会改选区），再慢慢滚。
3. 若出现"画面没有变化"提示，说明滚轮还是没落到内容上；把 `%TEMP%\LongShot_band.log` 的最后几行
   发我，`under=` 会直接指出滚轮落到了哪个窗口。

### 11.3 原因一：匹配率阈值把真实位移误判成 JUMP

样本 `D:\Temp\LongShot_65025125`（41 帧 906x1425，任务管理器进程列表）：
- 之前 37/40 对被拒 → 输出 54150（等于逐帧堆叠 41 屏）。
- 真实位移是唯一的强峰，但匹配率只有 71~78%：因为选区里夹着**不滚动的固定区**
  （左侧导航栏 x[0,90) 行匹配 30%、右侧滚动条/边框 x[810,906) 行匹配 4%），把整行平均 MAD 拖死。
- 阈值从 80% 放到 **70%**（`fMatched * 10 < fTextured * 7` 才拒绝）。

### 11.4 原因二：不滚动的工具栏/列头/状态栏被当成新内容重复拼接

日志里 `align:` 新增次优峰诊断 `second=<s>/<score>`。新发现：即使位移对了，
截图里那些**固定不动的行**（标题栏、工具栏、列头、状态栏）也每秒都在每一帧的同一行号出现，
拼完就是"一屏一屏的窗口叠在一起"。

`stitch.ps1` 新增 `StaticBand(packed, stride, effH)`：
- 判据：同一行号在相邻两帧里**逐像素完全一致**，且这种一致出现在 >=60% 的帧对里 → 该行是固定 UI。
- 允许带内有少量变化行（工具栏上的 CPU 数字/时间/进度一直在变），连续 10 行不静态才算带结束。
- 取顶部/底部的连续段，上限 effH/3；裁掉后不再参与对齐评分（顺带把匹配率抬高），
  拼接时只在整图**顶部和底部各画一次**（取自第一帧），画布相应加高 staticTop+staticBot。
- 日志新增 `static=topN bottomM contentH=K`。

## 十三、2026-11-11：为什么“老是合成失败”——帧间完全没有重叠

用用户 02:0x 的四次真实测试帧复现（都是 Chrome 窗口）：

| 帧目录 | 选区 | 帧数 | 结果 | 诊断 |
| --- | --- | --- | --- | --- |
| LongShot_79576171 | 1596×1012 | 9 | 失败（9108/8 跳） | 相邻帧位移 ≈ 1012px ≈ 整个选区高度 → **零重叠** |
| LongShot_80282218 | 871×288 | 9 | 失败 | 选区只有 288px 高，每帧滚 300px+ → 零重叠 |
| LongShot_80266515 | 434×298 | 6 | 失败 | 同上 |
| LongShot_79458828 | 989×795 | 6 | 成功 2412 | 选区够高、帧间有重叠 |

### 13.1 判定证据（不是猜的）

把 A 帧的**底部 320 行**和 B 帧的**顶部 320 行**上下拼起来看接缝（`D:\Temp\deveco\seam_check.png`）：
两段内容是**紧接的**，没有任何重复行 → 两帧之间没有一像素重叠，位移 ≈ 整个窗口高度。
这类情况在数学上不可能拼接（中间那段内容根本没被拍到）。

根因：`SettleMs = 420ms` 时，用户连续滚轮（日志里约每 30~190ms 一格，Chrome 一格 ≈ 100px），
两帧之间滚了 ~1000px，正好等于 1012px 的选框高度。

### 13.2 改动

1. `LongShot.ahk`：`SettleMs` 420 → **160ms**（帧密度 ×2.6，帧间重叠 ≈ 60%）。
2. `stitch.ps1`：`noscroll` 的判据改成“**每一对都成功对齐在 0**”（=画面真的没动）；
   新增 `nooverlap`（帧有变化但一对都对齐不上 = 滚太多，物理上拼不了），
   写进 `stitch_status.txt` / stdout：`OK h discontinuities=n noscroll=x nooverlap=y`。
3. `LongShot.ahk` 结束提示分三种：
   - `noscroll=1` → “没有检测到滚动…”（滚轮没滚到内容）
   - `nooverlap=1` → “拼不起来：相邻两帧完全没有重叠…请把选框拉高/每次少滚一点”
   - `discontinuities>0` → “已保存，但有 N 处接缝没对齐，那几处是直接续接的，可能重复一小段”

### 13.3 试过但无效的改法（别再试）

- 行像素容差 6 → 12：Chrome 的帧确实能对齐了，但**已知好样本会塌**：
  65025125 11761→10854、79458828 2412→797（内容被错误重叠吃掉）。危险，已放弃。
- 对齐前 3×3 模糊（半径 2）：对 Chrome 无效（真正的原因不是抗锯齿，而是零重叠），
  且对好样本有轻微退化（58197828 8677→8839）。已放弃。

结论：**Chrome 页面的帧和 Explorer 一样是可以逐像素对齐的**（79458828 成功即证），
前提是**帧间必须有重叠**。所以真正要保证的是“每次滚动的距离 < 选框高度”。
